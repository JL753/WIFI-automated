## 一、先记住四句话

1. **它测的是「两台设备之间、WiFi 链路上，应用层实际能跑多少数据」**，单位是 Mbit/s（Mb/s）。
2. **方法是真实打流**：一台手机当服务端、另一台当客户端，用内置的 **iperf3 3.22** 连续发送 TCP 或 UDP 数据，逐秒统计。
3. **数字不是估算的**：不是拿信号强度、也不是拿 WiFi 协商速率去推，每一个速率都来自 iperf3 自己打印的原始行，原始行会随结果包一起保存，可以逐条核对。
4. **它适合回答「这条链路能跑多快、稳不稳」**；不适合回答「时延多少、漫游快不快、几十台设备一起用会怎样」——这些见[第十节](#十能力边界与-wifi-测试行业覆盖)。

## 二、打流（吞吐量测试）是什么

### 2.1 用「水管」来理解

想知道一根水管每秒能过多少水，有两种办法：

- 看水管标称口径（对应 WiFi 的**协商速率**）——快，但只是理论值；
- 真的把水通进去，在另一头接住称重（对应**打流**）——慢一点，但量到的是真实流量。

打流就是第二种：一端不停往另一端发数据，另一端不停收，看每秒到底过去了多少。它是网络行业最基础、也最常用的吞吐量测试方法。

### 2.2 和几种常见「测速」的区别

| 方式 | 实际测的是什么 | 受什么影响 | 适合回答 |
| --- | --- | --- | --- |
| 手机 WLAN 详情里的「连接速度 / 协商速率」 | 空口理论速率（PHY 速率） | 信号、频宽、天线数、协议能力 | 这条链路大概是什么档次 |
| 测速网站 / Speedtest | 到互联网服务器的端到端带宽 | 宽带出口、测速服务器、路由器 | 我上网体验怎么样 |
| 下载一个大文件 | 应用层吞吐，但包含服务器、磁盘、协议开销 | 服务器限速、文件源、并发 | 直观感受快不快 |
| **本工具（iperf3 打流）** | **两台指定设备之间的局域链路吞吐** | 只受这条 WiFi 链路和两端设备影响 | 问题在路由器、WiFi 还是手机 |

一句话：**别的方式变量太多，本工具把变量收拢到「这两台设备、这一段 WiFi」上**，所以适合做对比和定位。

### 2.3 为什么必须两台设备

- 一台设备自己发、自己收，数据根本没经过空口，测出来是内存和 CPU 的速度；
- 分成「发」和「收」两端，才能分别看到**发送端推得动多少**和**接收端真的收到多少**。这两个数在链路有问题时会分叉，是判断丢包/重传的关键（见 [4.4](#44-发送端和接收端为什么有两个数)）。

### 2.4 一次测试里，数据走过的路

```
手机 A（客户端）                                   手机 B（服务端）
 ┌──────────┐    TCP/UDP 数据流                      ┌──────────┐
 │ iperf3   │ ────────────────────────────────────► │ iperf3   │
 │ 进程     │                                       │ 进程     │
 └────┬─────┘                                       └────┬─────┘
      │ 系统 socket / TCP/IP 栈                           │
      │ WiFi 驱动 → 空口发射 ──► AP/热点/群主 ──► 空口接收 │
      │                                                  │
      └──────────── 这一段才是 WiFi 链路 ────────────────┘
```

这条路上的任何一环都可能成为瓶颈：手机 CPU、发热降频、省电策略、WiFi 干扰、AP 转发能力、距离和遮挡。**打流量到的是整条路的结果，不是某一环的理论值**——这正是它可信、也是它需要控制变量的原因。

## 三、系统是怎么搭起来的

### 3.1 两个角色

| 角色 | 在干什么 | 关键点 |
| --- | --- | --- |
| **服务端** | 运行 `iperf3 -s`，监听 5201 端口，等对端来打流 | 一台手机点「当服务端」；锁屏、切后台不影响（App 起了前台服务） |
| **客户端** | 运行 `iperf3 -c`，连上服务端，按参数发/收数据 | 另一台手机点「开始打流」；结束时生成结果包 |

谁当服务端更好？建议**离路由器/热点更近、性能更好的那台**，因为服务端要处理所有并发流的收或发。

### 3.2 三种模式，测的是三段不同的链路

| 模式 | 拓扑 | 打流路径 | 能说明什么 |
| --- | --- | --- | --- |
| **WiFi** | 两台手机连同一个路由器/热点 | 手机 → AP → 手机 | 日常使用最常见；结果包含 AP 的转发能力 |
| **热点** | 一台开系统便携热点（SoftAP），另一台连上 | 手机 → 开热点手机 → 手机 | 这台手机当热点时的能力；没有路由器参与 |
| **P2P** | Wi-Fi Direct 点对点组网 | 手机 → 群主手机 → 手机 | 排除路由器，测两台手机之间的直连链路 |

三种模式用的都是同一套 iperf3 和同一套统计口径，**只是链路不同**。所以不要拿热点模式的结果去和路由器模式的结果直接比大小。

### 3.3 点「开始打流」之后发生了什么

1. 客户端读参数、做合法性检查，把**发起测试这台手机**的设备信息写进结果包（型号、系统、电量、WiFi 频段/信道/RSSI、协商速率等）。
2. App 拉起内置的 iperf3 子进程（不需要 root，也不需要另外安装）。
3. iperf3 每到一个采样间隔（默认 1 秒）打印一行统计。
4. App 逐行解析成一条记录（Record），同时写进日志、画进实时曲线。
5. 测试结束，iperf3 再打印一条**全程汇总行**；App 从两端输出里取「发送端 / 接收端」两个速率。
6. 客户端把结果包上传给 PC（如果配了地址），并在本机历史里留一份完整日志和结果。

### 3.4 数据流（谁产出、谁保存）

```
iperf3 输出行
   │  逐行正则解析（Parsed.java）
   ▼
Record（18 个字段，含原始行 raw）
   ├─► 实时日志 / 实时速率曲线
   ├─► 本机历史记录（完整日志 + 客户端结果包）
   └─► 结果包 JSON（schema: wifitput.result/1）──► PC 端接收器
                                                       │
                                                       ▼
                                        report.py → 逐秒明细.csv / 汇总.json / 测试报告.md
```

**整条链路没有云端参与**：数据只在两台手机和你的 PC 上。

## 四、一个速率是怎么算出来的

### 4.1 先看 iperf3 的原始行

App 日志里你看到的每一行，几乎都长这样：

```
[  4]   0.00-1.00   sec  21.8 MBytes  182 Mbits/sec  0             sender
```

逐字段拆开：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `[  4]` | 第 4 号流 | `-P 4` 时的其中一条连接；`[SUM]` 表示所有流的合计 |
| `0.00-1.00` | 区间 | 这条数据统计的时间段（第 0 秒到第 1 秒） |
| `21.8 MBytes` | 传输量 | 这个区间里传过去的字节数 |
| `182 Mbits/sec` | 速率 | 这个区间的平均速率 |
| `0` | 重传 | TCP 是重传次数；UDP 发送端是数据报总数 |
| `sender` | 角色 | 这一行是发送端视角；`receiver` 是接收端视角 |

UDP 接收端还会多出 `jitter`（抖动）和 `lost/总包 (丢包率)`。

### 4.2 速率的公式

```
速率（bit/s） = 区间内传输的 bit 数 ÷ 区间秒数
```

**这个除法是 iperf3 自己做的**，App 不重新计算速率，只做单位换算和统计。所以你在任何地方看到的速率，都能在原始行里找到对应数字。

### 4.3 单位里的坑：MBytes 和 Mbits 不是一回事

- `MBytes`（传输量）用的是 **1024 进制**：1 MBytes = 1024 × 1024 字节；
- `Mbits/sec`（速率）用的是 **10 进制**：1 Mbit/s = 1,000,000 bit/s；
- 1 字节 = 8 bit。

拿上面的例子手算核对：

```
21.8 × 1024 × 1024 × 8 ÷ 1,000,000 ≈ 182.9 Mbit/s
```

和 iperf3 显示的 182 对得上（差一点是因为显示的 21.8 已经四舍五入过）。
**有人拿「21.8 × 8 = 174」去质疑数字不对，是把 MiB 当成了 MB。**

App 界面统一显示 **Mb/s**，结果包里也会写明原始单位（`rate_unit`）。

### 4.4 发送端和接收端：为什么有两个数

| 方向 | 谁在发（sender） | 谁在收（receiver） | 两个数字从哪来 |
| --- | --- | --- | --- |
| 正向（默认） | 客户端手机 | 服务端手机 | 发送端 = 客户端自己的行；接收端 = 通过 `--get-server-output` 从服务端带回 |
| 反向（`-R`） | 服务端手机 | 客户端手机 | 发送端 = 服务端上报的行；接收端 = 客户端自己的行 |

- **发送端**：数据写进本机 socket 的速度，表示「我推得动多少」；
- **接收端**：对端真正读到的速度，表示「实际到了多少」。

链路有丢包、重传、对端 CPU 跟不上时，两者会分叉。**对外报「这条链路能跑多少」，优先用接收端数字**；发送端数字用来判断瓶颈在发的那一侧。

> 小提示：反向（`-R`）时，客户端看到的「发送端」数据来自服务端上报的 `Server output:` 段，这一段只用来到速率，不写进逐秒明细 CSV。

### 4.5 多流（`-P`）和 SUM

- `-P 4` = 同时开 4 条独立连接；
- `[SUM]` 行是 4 条流的合计；
- **单流**回答「一个应用（一个下载、一个视频流）能跑多快」；
- **多流**回答「这条链路总共能跑多快」。

两者不能直接比较：多流能更好地填满空口和 TCP 窗口，通常比单流高。报告里会写明用了几个流。

App 在画实时曲线时：有 `[SUM]` 就用 `[SUM]`，没有（单流）就用那一条流的速率；多流但缺 `SUM` 行时，把同一秒各流相加。日志和报告里的数字不受影响，各自按行呈现。

### 4.6 逐秒行 vs 全程汇总行

一次 10 秒测试，iperf3 会打印：

```
[  4]   0.00-1.00   sec   21.8 MBytes   182 Mbits/sec  0   sender   ← 逐秒行
[  4]   1.00-2.00   sec   22.4 MBytes   188 Mbits/sec  0   sender   ← 逐秒行
...
[  4]   0.00-10.00  sec  220.5 MBytes   184 Mbits/sec  0   sender   ← 全程汇总行
```

- 逐秒行说明「每一秒怎么样」；
- 汇总行说明「整段平均怎么样」，**它不是最后一秒**；
- 报告里的「平均」取自汇总行，「最低/最高」取自逐秒行。

### 4.7 采样间隔：每一行是「平均值」，不是「瞬时值」

- 默认采样 1 秒：每行是这一秒的平均；
- 调成 3 秒：每 3 秒一行，每行是这 3 秒的平均，曲线更平滑，但短时间的抖动会被抹平；
- 某一行显示 `0.00 bits/sec`，表示这一整个采样区间**一个数据包都没过去**，不是四舍五入的误差。

想看抖动就用小间隔，想看整体趋势可以放大间隔。

### 4.8 App 解析数据时做了什么、没做什么

- **做**：按 iperf3 的行格式识别数字行；表头、分隔线、连接控制行忽略；把数字存成 18 个字段（含 `raw` 原始行）；单位换算；统计平均/最低/最高。
- **不做**：不根据信号强度推算速率，不插值补齐缺失的秒，不修改 iperf3 报出的速率。
- 「发送端 / 接收端」汇总速率的选取规则：有 `[SUM]` 用 `[SUM]`，没有就用最后一条带角色的流；正反向都按角色（sender/receiver）取，不按「哪台手机」取。

## 五、每个参数如何影响结果

| 参数 | 默认 | 含义 | 怎么选 | 对数字的影响 |
| --- | --- | --- | --- | --- |
| **时长** | 10 秒 | 单轮打流秒数（App 允许 1–3600） | 快速对比 10–30 秒；看稳定/发热 300 秒以上 | 时间越长越接近稳态，也越容易遇到发热降频、省电、干扰 |
| **并发流** | 4 | iperf3 `-P`，同时开几条连接（1–32） | 模拟单应用用 1；测链路容量用 4–8 | 多流通常高于单流；流太多会增加两端 CPU 负担 |
| **采样间隔** | 1 秒 | iperf3 `-i`，多久打印一行（1–60） | 看抖动 1 秒；长时间跑可放大到 3–5 秒 | 间隔越大越平滑，越难看到瞬时卡顿 |
| **协议** | TCP | TCP 可靠传输 / UDP 不可靠传输 | 日常体验用 TCP；丢包、抖动用 UDP | TCP 会重传、受窗口和 RTT 影响；UDP 能看到真实丢包和抖动 |
| **方向** | 正向 | 正向 = 客户端发、服务端收；反向 = 加 `-R`，服务端发、客户端收 | 上下行分别测，两边能力可能不对称 | 上下行速率经常不一样，不能只测一个方向就下结论 |
| **UDP 限速** | 50M | UDP 发送端的目标速率 | 想测极限就逐步提高，直到开始丢包 | 这是**目标值**：写 50M 测出 50M 只说明「50M 能跑」，不代表链路极限 |
| **端口** | 5201 | 服务端监听端口 | 默认即可，被占用时再改 | 不影响速率，只影响连通 |

**参数必须成对比较**：时长、流数、协议、方向、间隔任何一项不同，两个结果就没有可比性；报告里会把这些参数完整记下来。

## 六、结果存在哪、报告怎么读

### 6.1 三层数据

| 层次 | 内容 | 位置 | 用途 |
| --- | --- | --- | --- |
| 实时 | 日志 + 实时速率曲线 | App 界面 | 现场判断有没有跑起来、有没有卡顿 |
| 本机历史 | 完整日志 + 客户端结果包，最多 50 条 | `/data/user/0/com.wifitput.android/files/history`；同步镜像到 `/storage/emulated/0/Android/data/com.wifitput.android/files/history` | 事后复盘、USB 导出 |
| PC 报告 | `逐秒明细.csv` / `汇总.json` / `测试报告.md` | PC 端接收器的工作目录 | 归档、对比、对外发报告 |

数据不经过云端。手机端会用与 `report.py` 相同的统计口径在本地算一份结果卡（主速率、最低/最高、重传/丢包、与协商速率的比例），也能把逐秒明细导出成 CSV（列顺序与 `report.py` 一致）；完整的 CSV/JSON/Markdown 报告仍由 PC 端和命令行工具共用的 `report.py` 渲染，所以三端口径一致。

### 6.2 测试报告的六个部分

| 章节 | 内容 |
| --- | --- |
| 一、结论摘要 | 自动生成的判断：客户端/服务端速率、实测占协商速率的比例；UDP 还会写抖动和丢包。这里的「客户端」指发起打流的那台手机 |
| 二、测试参数 | 时长、流数、采样、方向、协议、UDP 限速、端口、iperf3 版本 |
| 三、设备信息 | 型号、系统、电量/温度、内存、SSID/BSSID、频段/频率/信道、RSSI、协商速率、802.11 标准 |
| 四、测试结果 | 每个测试项的发送端/接收端速率、逐秒明细（前 10 行）、统计行 |
| 五、亮灭屏对比 | 只有命令行工具做过亮灭屏测试才有；手机 App 不产生 |
| 六、异常与提示 | 丢包率过高、WiFi 未连接、测试失败等自动提示 |

### 6.3 `逐秒明细.csv` 的列

| 列 | 含义 |
| --- | --- |
| 时间 / 测试 / 类型 / 线程 | 记录时间、测试编号、TCP/UDP、流号或 SUM |
| 起 / 止 / 传输量 / 单位 | 区间起止秒、这段时间传了多少字节 |
| 速率 / 速率单位 | 这段时间的平均速率 |
| 重传或数据报 | TCP 重传次数；UDP 发送端的数据报总数 |
| 抖动ms / 丢包 / 总包 / 丢包率 | UDP 接收端的质量指标 |
| 方向 | sender / receiver |

CSV 不含原始文本行；原始行在结果包 JSON 的每条记录的 `raw` 字段里。

### 6.4 报告统计口径

| 指标 | 从哪来 | 口径说明 |
| --- | --- | --- |
| 平均速率 | 全程汇总行 | 整段平均，不是各逐秒行的简单平均 |
| 最低 / 最高 | 逐秒行（有 SUM 用 SUM） | 多流时只看合计行，避免拿单流去和合计比 |
| 传输量 | 全程汇总行；没有则逐秒相加 | 同一份数据不重复相加 sender/receiver |
| 停滞秒数 | 逐秒行中速率为 0 的秒数 | 「中途卡死」的关键信号，平均值会掩盖它；长稳测试的结论会直接写出来，其他测试看逐秒明细 |
| 重传合计 | 整段汇总行 | 多流时取 SUM 的整段值，避免重复计数 |
| 抖动 | UDP 接收端 | 相邻数据报传输延迟的变化，不是时延 |
| 丢包 / 总包 / 丢包率 | UDP 接收端 | iperf3 按序列号统计 |

### 6.5 每个显示项的数据来源对照

| 你看到的 | 原始来源 | App/报告做了什么 |
| --- | --- | --- |
| 实时曲线上的点 | 逐秒行的 `rate` | 多流按 SUM/相加合并，单位统一为 Mb/s |
| 「发送端 xxx Mb/s」 | 汇总行或最后一条 sender 行 | 取整段速率 |
| 「接收端 xxx Mb/s」 | 对端 iperf3 的 receiver 行 | 正向经服务端上报取回，反向由本机统计 |
| 报告里的平均/最低/最高 | 汇总行 + 逐秒行 | 单位归一后统计，规则见 6.4 |
| 重传/丢包/抖动 | 原始行的对应字段 | 取整段值或最后一条有效值 |
| 设备信息 | Android 系统 API | 测试开始时拍一张快照，不是全程序列 |

### 6.6 为什么说数据可追溯

1. **每条逐秒记录都保留 `raw` 原始行**：结果包 JSON 里能逐条对照 iperf3 原文。
2. **历史记录保留完整日志**：手机上能翻到当次运行的每一行。
3. **参数和发起端设备信息写进报告**：用了什么参数、在什么环境下测的、发起测试的是哪台手机，全部留痕（服务端手机的信息见 10.4 的说明）。
4. **三端同一套渲染**：手机、PC、命令行产出同格式报告，不会各算各的。

## 七、数据可信度：什么时候成立、什么时候不成立

### 7.1 可信度的四个支点

1. **真实流量，不是估算**：数据从 iperf3 的 socket 收发里来，绕过了「看信号条猜速度」。
2. **两端交叉验证**：发送端和接收端各有一份数字，分叉本身就是线索。
3. **原始数据可审计**：速率、传输量、重传、丢包都能回到原始行核对。
4. **参数可复现**：同样的设备、参数、位置，可以重复测；报告里参数齐全。

### 7.2 会让数字失真的情况

| 现象 | 可能原因 | 怎么识别 | 怎么处理 |
| --- | --- | --- | --- |
| 发送端高、接收端低 | 丢包/重传、对端 CPU 跟不上、驱动瓶颈 | 两个数分叉；TCP 重传多 | 看接收端；换性能更好的设备做服务端 |
| 平均正常，但出现 0 Mb/s 的秒 | 空口竞争、AP 调度、手机卡顿 | 最低速率为 0、逐秒明细里有 0 的行（长稳测试会直接给停滞秒数） | 换信道/靠近 AP/关后台再测 |
| 一次高一次低 | 干扰、邻居设备、信道占用 | 多跑几次差异大 | 固定位置和信道，取 3 次中位数 |
| 越跑越低 | 手机发热降频、省电策略 | 曲线前高后低；设备温度 | 缩短单轮或冷却后再测，记录温度 |
| 单流低、多流高很多 | TCP 单流受窗口/RTT/丢失影响 | 参数对比 | 用多流测链路容量，用单流测应用体验 |
| 信号满格但速率上不去 | 手机 CPU、AP 转发能力、2.4G 干扰 | 对比不同设备/模式 | 换 5G 频段、换 AP 或换手机复测 |
| 协商速率 866，实测只有 300 多 | 空口开销、半双工、竞争、加密 | 属正常现象 | 用「实测吞吐」对外，不要拿协商速率当结果 |
| UDP 写 50M 就测出 50M | 这是发送目标，不是链路极限 | 看丢包率是否接近 0 | 逐步提高限速，直到开始丢包才是极限附近 |

### 7.3 对外汇报时，把话说完整

建议按这个模板说，别人很难挑刺：

> 在 <地点/环境>，<手机 A 型号> 与 <手机 B 型号> 通过 <路由器型号/热点/P2P> 连接，
> 频段 <2.4G/5G>、信道 <N>、RSSI <xx dBm>，使用 **TCP 正向、4 流、30 秒、采样 1 秒** 打流，
> **接收端平均 <xxx> Mb/s，最低 <xxx>，最高 <xxx>，重传 <n> 次**；重复 3 次，中位数 <xxx> Mb/s。

比「我测出来 300 兆」可信得多，因为参数、环境、统计口径都交代清楚了。

## 八、做一次可信测试的检查清单

**测之前**

- [ ] 两台手机连的是**同一个** AP / 热点 / P2P 群组，没有一台走移动数据；
- [ ] 记录位置和距离，尽量固定；避开微波炉、蓝牙音箱、金属遮挡；
- [ ] 关闭后台下载、系统更新、视频 App；两台手机电量充足、不过热；
- [ ] 确认两台手机的屏幕状态一致（亮屏/灭屏策略会影响省电和调度）；
- [ ] 想清楚这次要回答什么问题：单应用体验（单流）还是链路容量（多流）。

**测的时候**

- [ ] 参数成对比较：时长、流数、协议、方向、采样间隔保持一致；
- [ ] 看实时曲线有没有掉到 0、有没有持续下滑；
- [ ] 至少跑 3 次，不要拿最好的一次当结论，也不要只拿最差的一次。

**测之后**

- [ ] 记录两台手机的 SSID、频段、信道、RSSI、协商速率（报告里会自动带发起端的信息）；
- [ ] 看接收端速率、最低值、逐秒明细里的 0 速率秒、重传/丢包，不要只看平均值；
- [ ] 保留结果包和报告，必要时回看 `raw` 原始行；
- [ ] 换位置/换设备/换模式复测，确认问题是链路、AP 还是某一台手机。

## 九、常见误区

**Q1：手机 WLAN 里显示 866 Mbps，为什么测出来只有 300 多？**
协商速率是空口的理论峰值，不扣协议开销、管理帧、竞争退避、半双工等待和加密开销；实际吞吐通常是协商速率的 30%–60%，受环境影响很大。**报数用实测吞吐，不要用协商速率。**

**Q2：为什么发送端和接收端不是同一个数？**
测量点不同：发送端算的是「写进 socket 多少」，接收端算的是「真正读到多少」。中间有丢包重传、缓冲、对端处理能力。**对外用接收端。**

**Q3：为什么多流比单流快？**
多流能同时占用更多空口机会、把 TCP 窗口填满；单流受拥塞控制和 RTT 限制，经常填不满。两者回答的问题不同，不能混着比。

**Q4：UDP 限速写 50M，测出来就是 50M，说明链路有 50M 吗？**
只能说明「50M 这个速率能跑通」。要看极限，就逐步提高限速，直到接收端开始明显丢包。

**Q5：平均值挺高，为什么实际用起来会卡？**
平均值会掩盖短时间的 0 速率和抖动。看最低速率和逐秒明细里有没有 0 速率的行；UDP 还要看抖动和丢包。

**Q6：同样的手机，为什么今天和昨天测的不一样？**
WiFi 是共享介质，邻居信道、AP 负载、手机温度、后台应用都会变。固定条件、多测几次取中位数。

**Q7：这个数能代表宽带套餐的速率吗？**
不能。宽带是到运营商的出口带宽，本工具测的是手机到另一台设备的局域网 WiFi 链路，路径完全不同。

**Q8：为什么 P2P 模式和 WiFi 模式结果不能直接比？**
链路不一样：一个经过路由器，一个是两台手机直连。比大小之前先确认拓扑相同。

## 十、能力边界与 WiFi 测试行业覆盖

### 10.1 这个工具覆盖了哪些测试维度

| 测试维度 | 是否覆盖 | 说明 |
| --- | --- | --- |
| 吞吐量（TCP/UDP，上下行） | ✅ 完整 | 本工具的主项 |
| 多流聚合能力 | ✅ 完整 | `-P 1–32`，SUM 合计 |
| 丢包率 / 抖动 | ✅ UDP 支持 | iperf3 按序列号统计，抖动是延迟变化不是时延 |
| 短时稳定性 / 卡顿 | ✅ 可观察 | 逐秒曲线、最低速率、0 速率秒；长稳测试的结论会汇总停滞秒数 |
| 长稳测试（多轮循环） | ◐ 部分 | 单轮可设最长 3600 秒，但没有「多轮循环 + 自动断线重连」；长时间受手机省电/发热影响 |
| 覆盖 / 信号质量 | ◐ 部分 | 测试开始时记录 RSSI、频段、信道、协商速率；可在不同位置重复测，但不是专业扫频/热力图 |
| 时延（RTT） | ❌ 不覆盖 | iperf3 标准输出不提供 RTT；UDP 的抖动不等于时延 |
| 漫游 | ❌ 不覆盖 | 不触发、不统计漫游切换 |
| 多终端并发 | ❌ 不覆盖 | 一轮一个客户端；多台手机可以各自跑，但没有协同编排 |
| 多 AP / 组网 | ❌ 不覆盖 | 只测两台设备之间这一条路 |
| 热点 / SoftAP | ✅ 覆盖 | 「热点」模式 |
| P2P / Wi-Fi Direct | ✅ 覆盖 | 「P2P」模式，含扫码组网 |
| 双频 / 信道对比 | ◐ 手工 | 需要手动切换后复测；结果里会记录频段/信道 |
| 应用层体验（视频/游戏） | ❌ 不直接覆盖 | 吞吐是代理指标；不测启动时延、卡顿率、QoE |
| 认证 / 入网测试 | ❌ 不是认证工具 | 见 10.2 |

### 10.2 和行业标准、认证的关系

- **iperf3** 是网络行业事实上的打流工具，不同厂商、不同实验室都在用；只要参数一致，结果可以横向比较。
- **RFC 2544**（网络互连设备基准测试）规定了吞吐量、时延、丢包率、背靠背等测试方法，通常针对交换机/路由器，有固定帧长、稳态和零丢包搜索流程。本工具**没有按 RFC 2544 的流程执行**。
- **RFC 6349**（TCP 吞吐测试框架）面向运营商链路，强调单 TCP 流、RTT/MTU 和多窗口测试。本工具的 TCP 测试思路相近，但**没有实现这套方法论**。
- **Wi-Fi Alliance 认证**使用实验室专用仪表和规定场景。本工具是工程验证/现场排查工具，**不是认证仪表，不能替代入网认证或合同验收的最终判据**；但可以作为过程证据和问题定位依据。

### 10.3 在一个完整 WiFi 测试计划里，它站在哪

一个完整的 WiFi 验收通常会按这个顺序做：

```
覆盖与信号 → 吞吐量 → 稳定性/长稳 → 时延/抖动 → 漫游 → 多终端并发
   （扫频）    （本工具）   （部分覆盖）    （UDP 抖动）   （其他工具）  （其他工具）
```

本工具负责**吞吐量**这条主线，并且能用 UDP 顺带看丢包/抖动、用逐秒曲线看短时稳定；其余维度需要配合专业工具完成。把它放在「吞吐量定位」这一步，而不是「全项认证」那一步，定位就对了。

### 10.4 App 自身的限制

- 设备信息只采集**发起测试的那台手机**；服务端手机的信息要翻它自己的历史记录/日志，不进入结果包。
- 设备信息是**测试开始时的快照**，不是全程连续记录（曲线只有速率，没有同步的 RSSI 轨迹）。
- 不做亮灭屏对比、不做多轮长稳编排（这些是命令行工具的能力）。
- Android 12 起 P2P 拿不到真实 MAC，扫码组网靠设备名认人，重名或改名可能认错（可改用手动组网）。
- 手机省电策略、发热降频会影响结果；关键测试建议插电、冷却、固定亮度后再测。

## 十一、术语表

| 术语 | 解释 |
| --- | --- |
| 打流 | 用工具持续发送数据流，测量链路实际能承载的吞吐量 |
| 吞吐量（Throughput） | 单位时间内实际通过的数据量，本文统一用 Mbit/s |
| 协商速率（PHY 速率） | 手机和 AP 协商出的空口理论速率，不等于实际吞吐 |
| 空口 | 手机和 AP/对端之间的无线传输介质 |
| AP | 无线接入点；路由器、手机热点、P2P 群主都可以充当 AP |
| SoftAP | 手机系统热点，让手机自己当 AP |
| STA | 工作在「客户端」模式的 WiFi 设备，比如连上路由器的手机 |
| Wi-Fi Direct / P2P | 两台设备不经过路由器直接组网，其中一台当群主 |
| TCP | 可靠传输协议，丢包会重传，适合模拟网页/文件类流量 |
| UDP | 不可靠传输协议，不重传，适合测丢包、抖动和给定速率下的表现 |
| 抖动（Jitter） | 相邻数据报延迟的变化量，单位 ms；不是时延本身 |
| 丢包率 | 应收未收到的包占比，UDP 测试才直接可见 |
| 重传（retr） | TCP 因丢包/超时重新发送的次数，消耗空口但不增加有效数据 |
| 并发流（`-P`） | 同时建立的连接数；SUM 是它们的合计 |
| 正向 / 反向（`-R`） | 客户端发/服务端收；服务端发/客户端收 |
| 采样间隔（`-i`） | 每隔多久输出一行统计；每行是该区间平均值 |
| RSSI | 接收信号强度，单位 dBm；数值越大（越接近 0）信号越强 |
| 频段 / 信道 | 2.4GHz / 5GHz 等，以及具体信道号；干扰和速率能力不同 |
| SUM | iperf3 多流时的合计行 |
